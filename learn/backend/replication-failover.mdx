# Replication and failover

**The question:** How does a replica keep up, and what happens when the primary dies?

**The short answer:** the primary streams its write-ahead log to each replica, which replays the same changes. When the primary fails, a separate manager fences it off and promotes a replica to take writes. With asynchronous replication, the last few commits can be lost in that switch.

## How much a commit waits

In PostgreSQL, replication is asynchronous unless `synchronous_standby_names` lists at least one standby. Then `synchronous_commit` decides what a commit waits for.

| `synchronous_commit` | The commit waits until | If the primary dies right after |
| --- | --- | --- |
| `local` | The primary has flushed its own WAL | Recent commits may be missing on the replica |
| `remote_write` | The standby has received the WAL and handed it to its OS | Safe unless the standby's OS crashes too |
| `on`, the default | The standby has flushed the WAL to disk | Safe unless both servers fail together |
| `remote_apply` | The standby has replayed it, so reads there see it | Safe, and reads on that standby see your own writes |

Each step down the table adds latency to every commit, because the primary waits for a round trip to the standby. The setting can be changed per transaction, so only important writes need to pay for it.

## A minimal setup

```ini title="primary: postgresql.conf"
# wait for any one of two standbys to flush each commit
synchronous_standby_names = 'ANY 1 (replica_a, replica_b)'
```

```ini title="replica_a: postgresql.conf"
# replica_a also needs an empty standby.signal file in its data directory
# create its slot on the primary first: SELECT pg_create_physical_replication_slot('replica_a');
# the password comes from ~/.pgpass, never from this file
primary_conninfo = 'host=198.51.100.10 port=5432 user=replicator application_name=replica_a'
primary_slot_name = 'replica_a'
```

## Pitfalls

- **Synchronous with one standby.** If the only synchronous standby goes down, every commit on the primary waits. Use `ANY 1` over two or more standbys.
- **Split brain.** If the old primary comes back still accepting writes, two servers diverge. Fence it before promoting, and let a tool with a consensus store decide who leads.
- **Failing over too eagerly.** A network blip that triggers a failover causes more downtime than it saves. Require several missed checks.
- **Replication slots that fill the disk.** A slot keeps WAL until its replica reads it. A replica that is gone for good can fill the primary's disk, so set `max_slot_wal_keep_size`.
- **A replica is not a backup.** A dropped table is replicated within a second. Keep real backups with point-in-time recovery.
- **Never testing it.** Run planned switchovers regularly, so the first failover is not during an outage.
