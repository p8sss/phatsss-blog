# Single sign-on with OIDC

**The question:** how does one login work across many apps?

**The short answer:** every app sends the user to the same OpenID Provider, the IdP. The first time, the user signs in and the IdP sets its own session cookie. After that, each app's redirect finds that session, so the IdP issues a code without asking again, and each app gets its own ID token and session.

## OAuth and OIDC are not the same thing

| | OAuth 2.0 | OpenID Connect |
| --- | --- | --- |
| Answers | What may this app access? | Who is this user? |
| Main token | Access token, for an API | ID token, for the app itself |
| Token audience | The resource server | The app's client id |
| Signal to request it | Any scope | The `openid` scope |
| Extra endpoints | Authorize, token | Discovery, JWKS, UserInfo, logout |

OIDC is a thin identity layer on OAuth's authorization code flow. That is why the redirects look the same as in the OAuth PKCE flow.

## Verifying the ID token

```ts title="verify-id-token.ts"
import {createRemoteJWKSet, jwtVerify} from 'jose';

const ISSUER = 'https://login.example.com';
const CLIENT_ID = 'mail-app';
// take jwks_uri from the IdP's /.well-known/openid-configuration document
const jwks = createRemoteJWKSet(new URL('https://login.example.com/oauth2/jwks'));

export async function verifyIdToken(idToken: string, expectedNonce: string) {
  // checks the signature, iss, aud, exp and nbf
  const {payload} = await jwtVerify(idToken, jwks, {
    issuer: ISSUER,
    audience: CLIENT_ID,
    algorithms: ['RS256', 'ES256'],
  });
  // the nonce ties this token to the login request this browser started
  if (payload.nonce !== expectedNonce) throw new Error('nonce mismatch');
  return {userId: `${payload.iss}|${payload.sub}`};
}
```

## Pitfalls

- **Keying users by email.** Emails change and can be reassigned. The stable identifier is the pair of `iss` and `sub`.
- **Skipping the audience check.** An ID token minted for another app on the same IdP is still validly signed. Only `aud` tells you it was meant for you.
- **Using the ID token to call APIs.** APIs should accept access tokens with their own audience, not ID tokens.
- **Assuming logout is single too.** Ending one app's session leaves the IdP session and the other apps alive. Use RP-initiated logout to end the IdP session, and back-channel logout so the IdP can tell each app to drop its session.
