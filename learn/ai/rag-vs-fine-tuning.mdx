# RAG vs fine-tuning

**The question:** When do you retrieve, and when do you train?

**The short answer:** Retrieve when the model is missing knowledge. Train when the model knows enough but behaves wrongly. Most teams need retrieval first, and many never need training at all.

## Try the prompt first

Both options are more work than a better prompt. Go in this order, and measure at each step:

1. **Write a clear prompt** with instructions and a few worked examples.
2. **Add retrieval** if answers need facts the model does not have.
3. **Fine-tune** only if a prompt with good examples still cannot hold the behaviour you need.

Newer models follow formats and instructions much better than older ones. Check that the problem still exists on a current model before you train.

## Using both

They are not exclusive. A common split:

- **Fine-tune for the shape** of the answer: the JSON schema, the tone, when to refuse.
- **Retrieve for the content** of the answer: the policy text, the order record, the latest price.

The tuned model then learns to use retrieved passages well. The facts still live in your index, where you can update and permission them.

## Pitfalls

- **Fine-tuning to add facts.** Training on a document does not make the model quote it reliably. It may mix it up with what it already knew. Use retrieval for facts.
- **Blaming the model for a retrieval miss.** When a RAG answer is wrong, first check whether the right chunk was retrieved at all. Most fixes are in chunking, search and ranking.
- **Training data that leaks.** A tuned model can repeat parts of its training set. Never train on data that some users of the model must not see.
- **No eval set.** Without a fixed set of test questions you cannot tell whether retrieval or training helped. Build the eval first.
